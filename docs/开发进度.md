### v0.2.1 — `e961a33`（2026-10-11 23:30）全量 `rustfmt` 格式统一（15 文件）

**做什么**：一次性把全部源码与测试对齐 `rustfmt` 规范，使「格式」从**长期 advisory WARN** 变为**阻断项**，防护网至此**零 advisory**。

**为什么此前一直不动**：`cargo fmt` 会产生**横跨 15 个文件、约 900 行**的改动，混进功能提交会淹没真实 diff。故一直排在所有实质改动之后，且按用户要求**分段来搞、一次一提交**。

**怎么改**：**逐文件 `git add` + commit**（15 个独立提交，消息统一 `style: rustfmt <文件名>`，每个可独立回滚）——tests 9（`d3c529f` batch1_regression · `94942d0` batch2_regression · `fef2d34` engine · `93d705c` juezhang_regression · `aa3f94d` plan_regression · `b8c78b7` r07_batch2 · `230d0c9` r07_batch3 · `2dcca2d` r07_batch4 · `8928afb` r13_regression）、src 6（`eae281d` bin/gbmj_gui · `5ea7b0a` decompose · `d4efdcd` fans · `aa904ed` main · `1fe1597` model · `e961a33` plan）。

**格式改动的等价性证明（不能默认「格式=安全」）**：`rustfmt` 不只是调空白——它会把**闭包块压成表达式**（`|s| { f(s) }` → `|s| f(s)`）、把 `=> { Set{..} }` 压成 `=> Set{..}`，属**结构级**改写。**逐 commit 取父/子版本、剔除空白/逗号/花括号后逐字符比对 ⇒ 15/15 完全一致**，再叠加 `cargo test` 141/0 与门禁 **9/9 逐字对拍**，确认零语义改动。

**⚠️ 归档一次事故与裁定（防后人重踩）**：`cargo fmt --all` 把 **8 个 CRLF 文件翻成 LF**（`fans`/`plan`/`gbmj_gui`/`engine`/`r07_batch3`/`main`/`decompose`/`model`）。实测根因：**`rustfmt` 的 `newline_style=Auto` 只在「无需重写」时保留原行尾；一旦有格式差异需要重写，整个文件被翻成 LF**。
- **裁定：接受 LF，不做字节级恢复，不新增 `rustfmt.toml`。** 实验依据：① 同一份已格式化内容，**LF 与 CRLF 下 `rustfmt --check` 都 exit 0** ⇒ EOL 翻转**不影响门禁判定**；② `newline_style="Unix"` 会让 CRLF 文件变红、`"Windows"` 会让 LF 文件变红（当前 17 LF + 2 CRLF 混合），**`Auto`（不加配置）是唯一两种都不红的取向**；③ 手动恢复 CRLF **无意义**——下一次 `cargo fmt` 会再翻回去。
- 索引侧全部 `i/lf`（`core.autocrlf=true` 在 add 时归一化）⇒ **提交内容不受影响**，仅工作树 EOL 为混合态（与仓库既有状态一致）。

**结果**：`cargo fmt --all -- --check` = **exit 0**；门禁由 `PASS 6 / WARN 1 / FAIL 0` 升为 **`PASS 7 / WARN 0 / FAIL 0`**。

### v0.2.0 — `b981716`（2026-10-11 23:19）魔鬼数字治理（番值裸数字 → 命名常量）

**做什么**：用户裁定「**不要搞魔鬼数字，那种有特定意义的数字换成常量**」。把测试里**有特定语义**的裸数字改为**命名常量**，让断言从「魔法数字」变成**可读、可核**的信息。

**为什么值得做**：裸数字断言（如 `assert_eq!(w.normal, 202)`）在失败时**无法定位是哪个番出错**；改常量后可读性、可诊断性都提升，且常量注释写明**番名与出处**。

**三批范围与结果**（共 **66 个命名常量**；**替换处数按口径不同**：开发自述「语义位置」计 **160 处**，Lead 按 diff 逐行粗筛（元组按 `("名", 值)` 逐项计）得 **292 处**——差异在于**同一行数组内含多个元组**、以及 `must`/`repeat` 表项的分项计法，**两者不矛盾，口径不同**；以 `tests/` 内常量引用总数 **311 次**（含定义与注释）为上限参照）：

| 批 | 范围 | 常量 | 提交 |
|---|---|---|---|
| **B 类：番值单点** | 左值为 `fan_value/val/val_of/val_t` 的断言，23 处 | 19 | `1772a4d`（batch1 17 处→15）· `f721053`（juezhang 3 处→`FAN_HE_JUE_ZHANG`）· `214c835`（r07_batch2/batch4 3 处） |
| **表驱动** | `must: &[("番名", 值)]` / `for (n,v) in [...]` 数据表，127 条目 | 64 | `f43cc89`（batch2 52 处）· `a0968da`（batch3 49 处）· `9f762ae`（batch4 26 处） |
| **C 类：四栏/距离** | 四栏单番值与组合和；距离类**判定不动** | 依 B/表驱动复用 | `2146f8e`（engine 23 常量）· `0c5fb06`（batch1 6 常量）· `b981716`（juezhang 复用） |

**两条关键语义区分（本轮最重要的技术判断）**：
1. **`must` 与 `repeat` 的数字语义不同** —— `must: &[(番名, u32)]` 的第二项是**番值和**（`assert_eq!(val(w,n), v)`）；而 `repeat: &[(番名, usize)]` 的第二项是**出现次数**（`count(f.name==n) == times`）。开发最初建议 `FAN_YAO_JIU_KE * 4`——**数值巧合正确但语义是错的**（把「出现 4 次」写成「番值 ×4」，一旦番值规则变动就会算错）。最终改为 **`TIMES_YAO_JIU_KE_4/3/2`** 并在注释注明「应出现 N 次（每副各计 1 次）—— **非番值**」。**为此类错误不会被任何测试或门禁捕获**，只能靠读消费代码发现。
2. **同一数字不同番必须分别命名** —— `64` 同时对应四暗刻/小三元/字一色/清幺九，**禁止合并成 `FAN_64`**；实测 24 番拆 5 个常量、64 番拆 3 个、2 番拆 7 个。

**判定原则（用户口径「不要为改而改」）**：
- **距离类 25 处一律保持字面量**（`d.distance == 0/1/2` 是**通用阈值**：0=已达成、1/2=差 N 张）；
- **`assert_eq!(w.normal, 10)` 这类含两次同番的组合**（如 `幺九刻` 出现两次）**保持字面量 + 补组成注释**，避免 `FAN + FAN` 冗余或 `FAN * 次数` 的语义混淆；
- **混合形态（元组右值 18 处、`assert!` 数值比较、`MAX_DIST`）本轮不做**，登记 backlog。

**常量注释出处修正（`f348442`，83 处）**：原名注写 `出处：src/fans.rs:815` 这类**行号引用**；因 clippy 修复在 `fans.rs` 前部插入行，**10 处整体漂移 3 行、4 处动态标注错位 2 行**（**门禁与 141 条测试全绿、无任何机制报错**）。经**全量扫描**（非抽查）发现后，统一改为**内容引用**（`f("四归一", 2)`），不再写行号。

**独立复验（`64edc48`，tester 异构复核）**：剥注释后按**多重集等价**逐条比对 ⇒ `52/52`、`49/49`、`26/26` **全部逐条等价、残留 0**；`repeat` 语义专项通过；用例名集合 141 与各文件 `assert!` 宏计数与基线完全一致；负向复核（改 `48→47` ⇒ 用例 FAIL `left:48/right:47`）证明**防护网对常量改错灵敏有效**。**结论：采信、推翻无。**

**结果**：`tests/` 内命名常量 **66 个**（`FAN_*` 63 + `TIMES_*` 3）；四栏类裸数字**仅剩 2 处**（即上述「保持字面量 + 组成注释」的裁定项）；测试 **141 passed / 0 failed** 全程不变。

**新增测试**：`tests/r13_regression.rs`（10 条，库级断言 `Direction.covered_by`）。

**顺带修正**：README 番种数由 `73` 改为「**静态注册 73 + 动态生成 4 = 共 77**」（测试定稿口径）。

**归档的口径分歧**（防后人重蹈）：测试曾把「清幺九 → 混幺九」判为**不成立**（理由：清幺九手零字牌）——那其实是**「双方都达成」读法**；按用户确认的 A 口径（**只看 coverer 是否达成**）该对**成立**：清幺九 ⊂ 混幺九 且 64 ≫ 32，属"低番路径被支配"。两种读法各自自洽，最终采用用户口径。同理，`清一色 → 混一色`、`字一色 → 混一色`、`九莲宝灯 → 混一色` 在 A 口径下**仍不成立**（字一色/九莲手零数牌或零字牌，混一色**仍需额外 1 张**，未被支配）——**若实现它们，等于把 R-08 假阳性换个形式复活**。
