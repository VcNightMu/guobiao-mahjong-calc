## 一、结论

**质量判定：需返工（计番正确性）。不建议在修复前把引擎输出的番数当权威结果使用。**

拆开看：

- **架构与测试基线健康，可接手**：引擎/CLI/GUI 分层清晰；`cargo test` 47/47 全绿（见 §二）。
- **但番种正确性没有测试兜底**：代码产出 77 个番种，其中 **48 个连一条「番种名级」断言都没有**，**39 个连间接的数值断言都没有**（见 §三）。
- **实测确认 4 个计番/显示缺陷 + 2 个高疑重复计番 + 3 个健壮性缺陷**（见 §六）。

| 编号 | 严重度 | 问题 | 一句话依据 |
|---|---|---|---|
| **A** | 高 | 荣和时「和牌张牌号 == 手里既有暗刻牌号」被一律判为明刻，即使和牌张实际补在顺子里 → 少算 双暗刻/三暗刻/四暗刻 | 同一手牌和 1万 少 2 番，和 4万/7万 却正常 |
| **B** | 高 | 暗牌里握 3 张同一张牌时，绝张**必然成立**，代码却判 `can_last=false` → 少算 和绝张 4 番并隐藏两栏 | `can_last = concealed[t] == 0`（src/calc.rs:240） |
| **C** | 高 | **P0 已复现**：可见的「点和/自摸」两栏都 < 8，界面却打 ✔（因为被隐藏的绝张栏 ≥ 8） | `111m 234s 45s 789s 99m` → `3条 5 7 — — ✔` |
| **D** | 中 | 组合龙与杠复合时，杠系番种整体漏算（README 自认遗留，实测确认） | 组合龙 + 暗杠 输出只有 16 番，无「暗杠2」 |
| **E** | 高（疑） | 字一色 与 混幺九 重复计番（+32） | `字一色64 混幺九32` 同现；同一份代码对 清幺九/混幺九 却用了 else-if |
| **F** | 中（疑） | 全大+大于五、全小+小于五 重复计番（各 +12） | `全大24 大于五12`、`全小24 小于五12` 实测同现 |
| **H1** | 中 | 手牌牌数、单张张数上限**完全不校验**，非法输入被静默算出「合理」番数 | 同一张牌 5 张的手牌照样给出 3 个听牌张与番数 |
| **H2** | 中 | `--round` / `--seat` 缺参数直接 panic | `src/main.rs:75:39 index out of bounds` |
| **H3** | 低 | `--round 乱写` 静默回落「东」；`parse_hand` 静默忽略非法字符 | src/main.rs:9-17、src/tiles.rs:130-133 |
| **I** | 低 | 文档陈旧：`src/fans.rs:7` 注释称「未实现：组合龙、推不倒」，实际均已实现 | fans.rs:97/174/784/788 就是实现 |

> 判定为「需返工」而不是「有阻塞风险」，是因为 A/B/C/D/E/F 都不是崩溃类问题，而是**静默算错**——这比崩溃更危险，且当前测试完全覆盖不到（见 §三）。

### 3.4 按风险给盲区排序（为什么这 39 个危险）

- **最危险：需要精确互斥的族** —— 三同刻/双同刻、双暗杠/双明杠/三杠/四杠、四归一、全双刻、双箭刻、小四喜、清幺九、混幺九、字一色。这些番种的价值全靠 `apply_exclusions`（src/fans.rs:848-971）的互斥表，**互斥表本身几乎没有测试**，而实测已经证明它漏了两条（见 §六 E/F）。
- **次危险：组合型大番** —— 一色四同顺/一色四节高/一色四步高/一色三步高/一色三节高。它们和「一般高/连六/老少副/套算一次」耦合，是计番最容易算错的地方。
- **再次：花色整手番** —— 全大/全中/全小/大于五/小于五/绿一色/断幺，全是「整手牌的属性」，容易和别的整手番重复叠加（F 即此类）。

## 四、高风险未覆盖区（README 自认遗留项 + 互斥/套算）

### 4.1 组合龙与杠复合 —— **实测确认是真缺陷**（缺陷 D）

README 第 97 行列为遗留。实测：

```powershell
cargo run --quiet --bin gbmj -- 147m 258s 369p 5p --ankan 1p
```
```
暗牌 10 张 | 副露 1 副 | 门清
结构听牌: 5筒

和牌张         点和      自摸      点和绝张        自摸绝张   够和
5筒           16      18         —           —   ✔

5筒: 组合龙12 单钓将1 无字1 门前清2
```
根因：`collect_special()`（src/fans.rs:83-199）**完全不计算任何杠系番种**；杠系逻辑只写在 `collect_standard()`（src/fans.rs:279-302）。组合龙走的是 special 分支，所以「暗杠2」被整体吞掉。正确应为 点炮 18、自摸 22（暗杠不破门清 → 不求人4）。凡是「组合龙 + 任意杠」都受影响，最高可差 88 番（四杠）。

### 4.2 全不靠三花色约束 —— **已论证不可能违约，这条遗留项无实际风险**

README 把「全不靠三花色约束」列为遗留。独立论证：`is_bu_kao`（src/decompose.rs:212-240）只要求「某一行列分配下，每门现有牌都落在自己的 147/258/369 列内」，并不强制三花色齐全。但**违约在数学上不可能**：

- 每门花色受列限制，最多只能贡献 3 张（列内只有 3 个不同点数），且 `x > 1` 直接否决；
- 两门花色最多 6 张，加上全部 7 张字牌 = **13 < 14**；
- 所以任何 14 张的合法全不靠**必然三花色齐全**。

结论：**无需修改**。（这是一条「看似有坑、实为安全」的结论，写在这里以免后续有人重复排查。）

### 4.3 互斥（`apply_exclusions`）与「套算一次」

- 互斥表有 848-971 共 ~120 行、约 40 条规则，**只有 3 条被断言**（大四喜、一色双龙会、推不倒/清一色 等少数几条）。实测已找到 **2 条漏互斥**：字一色 vs 混幺九（E）、全大/全小 vs 大于五/小于五（F）。
- 「套算一次」的贪心扩张算法（src/fans.rs:609-690）：
  - `tests/engine.rs:207/259/276` 三条用例覆盖了「花龙+套算一次」「一副顺子服务两个番种」「四副顺子套出 3 对」。
  - 我抽查的 `1122334455667m`（连七对听牌）与 `123456789m 55p 78s` 均未发现算少/算多。
  - **但贪心是启发式，不是最大匹配**；我没有做穷举对拍（见 §八「未做的验证」），这块**仍是覆盖缺口**，不能判定为「已验证正确」。

## 五、实测抽查（命令 + 原样输出 + 判定）

以下全部为真实执行结果。12 组用例，覆盖 §三 中零覆盖番种的一部分。

### 5.1 缺陷 A / B 的载体：`111m 23m 456m 999s 55p`

```
$ cargo run --quiet --bin gbmj -- 111m 23m 456m 999s 55p
暗牌 13 张 | 副露 0 副 | 门清
结构听牌: 1万 4万 7万 5筒

和牌张         点和      自摸      点和绝张        自摸绝张   够和
1万            8      12         —           —   ✔
4万            7       9         —           —   ✔ ✔仅自摸
7万            8      10        12          14   ✔
5筒            5       9         —           —   ✔ ✔仅自摸

1万: 幺九刻1 幺九刻1 连六1 无字1 四归一2 门前清2
4万: 双暗刻2 幺九刻1 幺九刻1 无字1 门前清2
7万: 双暗刻2 幺九刻1 幺九刻1 连六1 无字1 门前清2
5筒: 幺九刻1 连六1 无字1 门前清2
```
**判定（经 task-8 定案复核）：1万 行确认 bug（缺陷 A+B）；4万 / 7万 / 5筒 行正确。**

- 和 1万 时唯一分解是 `将55筒 / 111万 / 123万 / 456万 / 999条`：和牌前(13 张)手里就已经有 `111万`(3 张) 与 `999条`(3 张) 两个**已成型**的暗刻；和牌张 1万 实际补进 `23m` 这个两面搭子、组成 `123万` **顺子**（111万 三张 + 1万 一张 = 四张 1万，合法）。
- **正确番表（点和）= 幺九刻1 + 幺九刻1 + 连六1 + 无字1 + 四归一2 + 双暗刻2 + 门前清2 = 10**。引擎给 8，**少的正是 `双暗刻2`**；`四归一2` 引擎已正确计入，**四归一与暗刻系并不互斥**（自证见 §六 缺陷 A 的定案块）。
- **只影响「荣和」两栏**：`自摸 12` 引擎反而是对的（`src/fans.rs:322` 的 `!ctx.tsumo` 让自摸路径跳过了该错误判据）。所以 1万 应为：点和 8→**10**、点和绝张 12→**14**（该栏被 `can_last` 隐藏）、自摸 12 ✔、自摸绝张 16 ✔。
- 同一手牌和 4万/7万 时「双暗刻2」正常出现，**只有和牌张牌号恰好等于既有暗刻牌号时才丢**——这就是 A 的判别式。4万=7（分解 `111万+234万+456万+999条`）、7万=8（分解 `111万+234万+567万+999条`）**均正确**。
- 1万 的「点和绝张/自摸绝张」显示 `—`，但暗牌里 1万 已有 3 张，**第 4 张就是全牌池最后一张**，绝张必然成立、且不需要任何外部信息 → B。

```
5条: 幺九刻1 连六1 缺一门1 无字1 门前清2
```

  ```rust
      self.normal >= 8 || self.tsumo >= 8 || self.last >= 8 || self.tsumo_last >= 8
  }
  ```
  对比 `only_last()`（97-105）就带了 `self.can_last &&`；而 `src/main.rs:139` 的 ✔ 直接由 `can_win()` 决定，`src/main.rs:152-157` 又把两栏显示成 `—`。
- **复现**：`cargo run --quiet --bin gbmj -- 111m 234s 45s 789s 99m`
- **真实输出**：`3条  5  7  —  —  ✔`（可见两栏 5 和 7，均 < 8）
- **对照实验证明**：`cargo run --quiet --bin gbmj -- 111m 34s 678s 789s 99s` → `2条  5  7  9  11  ✔ ✔仅绝张`，番表与上例 3条 行**逐字相同**，可见绝张 = 点炮+4 = 9 ≥ 8。故上例 3条 行的隐藏值同样是 9，✔ 由被隐藏的栏决定。
- **结论：真实可达（不是理论缺陷）**。附带说明：这同时是「界面信息不完整」问题——用户看到 5/7 和 ✔，无从得知为什么能和。
- **GUI 同源**：`src/bin/gbmj_gui.rs` 与 CLI 共用 `analyze()`/`can_win()`，同一缺陷同样存在（本轮未启动 GUI 做像素级验证，仅代码同源性判断）。

## 七、待人工确认的规则口径（**不判为 bug**，如实记录分歧）

1. **`双同刻` 出现两组时是否应计两次。** §5.9 的四杠手有 `1万/1条` 与 `9万/9条` 两组同数刻子，工具只计一次 `双同刻2`。国标「不得相同原则」指「名称相同且组成元素也相同才不重复」，本例元素不同，**倾向应计两次（4番）**，但我未取到权威原文 → 存疑。
2. **`自摸绝张` = 自摸1 + 和绝张4 = 5番** 是产品口径（README 已声明四种和法）。官方「和绝张」通常限定荣和；此处属口径选择，不算 bug，但建议在 README/界面注明「自摸绝张」为非标准展示项。
3. **七对含四张同牌时不计 `四归一`**：`collect_special()` 不跑 `四归一`（`src/fans.rs:778-782` 只在 standard 分支）。是否应计，存疑。
4. **`一色四同顺` 是否应吞掉 `清一色/平和/全带幺`**：工具保留（§5.8）。官方「一色四同顺 不计 一色三同顺/七对/四归一/一般高」这条我认可，但 `清一色` 等是否也排除，本轮**未能取到权威原文**（见 §十「取源受限」）。
5. **`三风刻` 与 `圈风刻/门风刻` 是否互斥**：工具**允许叠加**（§5.10 之外的 5.12 是另一种情形；单独的 `东东东 南南南 西西西 456m 9m --round 东 --seat 南` 输出 `混一色6 三暗刻16 圈风刻2 门风刻2 幺九刻1 三风刻12 单钓将1 门前清2 = 42`）。我查到[百度百科「风牌刻」](https://wapbaike.baidu.com/item/%E9%A3%8E%E7%89%8C%E5%88%BB)称「大四喜…不计圈风刻、门风刻、三风刻、碰碰和」「小四喜…不计三风刻」「同时另有圈风刻计2番、门风刻计2番」，**倾向支持工具行为**；但百科非权威规则书 → 记为「未发现异常，建议按规则书复核」。
6. **`全大/大于五`、`字一色/混幺九` 的互斥原文**：我给出的判定依据是「子集关系 + 代码自身对同类关系的处理不一致」（强有力的内部矛盾证据），但**官方「不计」原文本轮未能取到**，故 §六 E/F 标注为「疑似」。
