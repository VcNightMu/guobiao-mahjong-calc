## 0. 一句话现状

Rust 写的国标麻将（中国麻将竞赛规则 1998）**听牌算番器**：给定「暗牌 + 副露 + 圈风门风」，枚举**结构听牌张**，并对每张听牌算出**四种和牌方式**（点和 / 自摸 / 点和绝张 / 自摸绝张）的番数。引擎已相当完整（47 个测试全绿；方案稿列出的 72 个番种在代码中均有实现路径），命令行可用，图形界面（egui/eframe）**可编译、release 产物已是最新（窗口未做交互点验）**。
**接手前请先看 §5 的 4 个 P0 缺陷**（均为已确认，不是猜测）：① 「够和 ✔」用隐藏栏判定（`can_win()` 未按 `can_last` 门控）；② 荣和暗刻误判（`fans.rs:322-324`）；③ 手握 3 张时绝张被误判不可达（`calc.rs:240`）；④ 文档与代码脱节（README 会让接手者找错文件、漏掉已交付的 `--plan`）。另有输入零校验（可给出"看似正常的错番数"）。

### 2.2 环境坑（README 已记录，本机已满足）

1. **MinGW + 中文路径**：`ld` 打不开 UTF-8 路径 → 工程必须放在纯 ASCII 路径。当前路径 `F:\AllCodes\guobiao-mahjong-calc` 是纯 ASCII，坑已规避。
2. **GUI 需要 64 位 MinGW-w64 的 `dlltool`（binutils ≥ 2.30）**：`eframe` 走 raw-dylib；若 `gcc -dumpmachine` 显示 `mingw32`（老 32 位 mingw.org 版）会报 `dlltool: Can't create .lib file: Invalid bfd target`。README 给的解法：`winget install BrechtSanders.WinLibs.POSIX.UCRT` 并确保其 `bin` 在 PATH 中。
3. **`.cargo/config.toml` 是历史残留**：文件只有注释，注释里写的路径是旧路径 `F:\ArkCodes\guobiao-mahjong-calc`（与当前 `F:\AllCodes\...` 不符），且该文件被 `.gitignore` 忽略。**不影响构建**（因为工程已在 ASCII 路径），但会误导接手者。实测：`cargo build` 正常，无需任何额外配置。

## 3. 架构分层与逐文件职责

### 3.1 分层

```
gbmj-gui (src/bin/gbmj_gui.rs)   ← 界面层：只做录入/展示，调用 calc::analyze
        │
gbmj    (src/main.rs)            ← 命令行层：参数解析 + 文本展示；调用 calc::analyze / plan::plan
        │
gbmj 库 (src/lib.rs)             ← 引擎层，无 UI 依赖
   ├── tiles.rs      牌编码/解析
   ├── model.rs      输入模型（副露、门清）
   ├── decompose.rs  和牌型分解
   ├── fans.rs       番种识别 + 互斥 + 计分
   ├── calc.rs       听牌枚举 + 四栏计算（对外主入口 analyze）
   └── plan.rs       未听牌方向扫描（对外入口 plan）
```

依赖方向单向：`bin → 库`；库内部 `calc → {decompose, fans, model, tiles}`，`plan → {decompose, model, tiles}`，`fans → {decompose, model, tiles}`。**引擎完全不依赖 eframe**，因此 `cargo test --no-default-features` 可无 GUI 环境运行。

### 4.3 番种覆盖（机械核对，可复现）

用脚本把「方案稿 §7 的番种名单」和「`fans.rs` 里的番种名」做集合比对，实测结果：

- `听牌算番方案-v0.1.md` §7 列出 **72 个唯一番种名**。
- `src/fans.rs` 中静态条目 `f("名", 番)` 共 **73 个唯一名**。
- 代码静态表**独有**：`门前清`、`不求人`、`自摸`、`和绝张`（这 4 个是**和法番**，不是牌型番，按口径单独叠加）、`无番和`（方案稿写作 `无番和(特殊)`）、`一明一暗杠`（工程自增）。
- 方案稿**独有**：`一般高`、`喜相逢`、`连六`、`老少副` —— 这 4 个在代码里是**动态计数**（`src/fans.rs:602-690` 注释「同一副顺子可以同时出现在不同番种里…」），不写在静态表里。
- 结论：**方案稿 §7 的 72 个番种在代码中全部有实现路径**；工程实际是「72 + 自增的一明一暗杠」。
- ⚠️ `README.md:96` 写「一明一暗杠…作**第 82 个**番种」，与本工程内枚举数（72 + 1 = 73）**不一致**；「82」的来源 **【未核实】**（疑似沿用了「国标 81 番种 + 自增 1」的常见说法，而工程自带的方案稿只列了 72 个）。接手时以代码/方案稿为准，遇到争议需重数官方条文。

## 6. 已知风险与陷阱（口径层面，改代码前必读）

1. **起和判定非单调**：`{0 → 无番和 8} ∪ {≥8}` 能和，`1..7` 卡死。因此**不能**用「番数越大越可能和」的直觉做剪枝；`base==0` 是一条独立的和牌路径（`src/fans.rs:1028-1032`，仅 `Normal` + 非门清 + `total==0`）。
2. **边张/坎张/单钓将要求整手独听**：必须在算出**完整听牌集**之后才能判（`src/calc.rs:176-187`），候选张之间**不独立**。`--plan` 里对同类结构番另有一份判断（`src/plan.rs`），两处改动要同步。
3. **绝张依赖外部信息**：牌河/明面信息算番器拿不到，只能按用户假设。代码用 `can_last = 暗牌里没有该张`（`src/calc.rs:240`）做**可达性近似** —— 这只是必要条件的近似，不是绝张判定本身。**注意 P0-1 就是这条近似的下游不一致。**
4. **不重复原则 = 两件事**：① 拆法搜索取最大（就高不就低，`jiu_gao_bu_jiu_di` 用例：48 vs 47 取 48）；② 结构性互斥查表（`src/fans.rs:900-971`）。**只做①不做②会系统性多算番**。
5. **暗杠不破门清**：判门清只看吃/碰/明杠（`src/model.rs:56-60`）。暗杠仍算门清 → 门前清/不求人照常成立。补杠按**明杠**处理（方案稿 §2 口径）。
6. **必然门清的牌型不再计门前清**（`src/fans.rs:982-984`：七对/连七对/十三幺/九莲宝灯/七星不靠/全不靠/四暗刻），自摸时只 +自摸 1 而不计不求人（`bi_ran_menqing_tsumo_is_just_one` 实测 24+6+1=31）。
7. **荣和补成的刻子算明刻**：同一张听牌，点和与自摸的**番表可能不同**（`ankou_differs_by_win_method`：12 vs 28）。所以 `WaitResult` 同时保存 `fans` 与 `fans_tsumo` 两份明细；任何"只存一份明细"的改动都会错。
8. **套算一次不是"一副顺子只能用一次"**：可以是"同一番种内不重复用，但同一副顺子可参与不同番种"，且计数按**对数**展开（`tao_suan_yi_ci_four_runs_three_pairs`：四副顺子套算出 3 对）。这句话很容易理解反，`fans.rs:602-690` 有专门注释。
9. **清龙成立时不拆移**（不计连六/老少副），但**孤立的顺子不该被牵连**（`lian_liu_survives_isolated_run`：567万配不上任何番，不能因此把 456条+789条 的连六一起挡掉）。
10. **花牌完全不参与**：34 种牌模型里没有花牌（`src/tiles.rs`），既不计番也不参与起和 —— 这是锁定口径，不是遗漏。
11. **不计偶然番**：抢杠和、海底捞月、妙手回春、杠上开花一律不算（`README.md:59`）。
12. **展示不做 8 番过滤**：<8 番也显示（`README.md:66`、`src/main.rs:137-161`、`gbmj_gui.rs` 用灰色显示），这是刻意设计，不要"顺手加过滤"。
